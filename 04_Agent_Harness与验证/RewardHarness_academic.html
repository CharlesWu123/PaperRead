一句话总结

核心命题

本文把 reward modeling 从"权重优化"改写为"上下文进化"：不训练任何参数，只用 100 条人类偏好示范，让一个 Orchestrator 反复自我诊断并演化出一套 Skills 与 Tools 文档库，驱动冻结 VLM 在图像编辑评测上取得 47.4% 平均排序准确率，比 GPT-5 高 5.3 分。

研究背景与动机

指令引导的图像编辑（instruction-guided image editing）在过去两年里成为生成模型的主战场之一，但它的评测一直是薄弱环节。判断一次编辑是否"好"，需要同时理解三个东西：源图 $I_s$ 表达了什么、编辑指令 $p$ 要求改什么、以及编辑结果是否在改到该改的地方的同时保住了不该动的部分。这种判断是细微的、多维的，且各维度之间存在优先级冲突——例如背景风格迁移成功但主体面部出现了扭曲，该判高分还是低分，取决于指令的语义边界在哪里。

主流做法沿着一条固定流水线走：收集大规模人类偏好标注，用这些标注对一个视觉语言模型做监督微调，得到专用 reward model，再把它的输出当作强化学习的 reward 信号去对齐生成器。这条路线在文本领域被验证得很充分，迁移到图像编辑上却付出了明显代价。本文在动机部分列出四点：标注成本高；需要额外的训练阶段；输出是一个不透明的标量分，无法解释它为什么这么打；以及最关键的一点——这套范式无法作用于只提供 API 的闭源基础模型，因为你根本拿不到权重去微调。

论文把这一现象概括为一个"数据效率 gap"。摘要原文的表述是："humans can often infer the target evaluation criteria from only a few examples, while models are usually trained on hundreds of thousands of comparisons." 人类评审看几个例子就能归纳出评价标准并写成打分细则，而模型要看几十万对比较才能学到近似的东西。这个落差提示，问题可能不在于"参数里存的偏好知识不够多"，而在于"评价标准这类知识本来就更适合以显式文本形式存在，而不是被压进权重"。

由此产生本文的出发点：如果评价标准可以写成人类能读的规则，那么让模型自己把这些规则写出来、试错、修订、淘汰，是否比用梯度把它们塞进参数更高效？Figure 1 用一张范式对比图回答了这个问题的定位——上路是传统范式（大规模偏好数据 → 训练 reward model → 作为 RL 对齐的 reward 信号），下路是 RewardHarness（少量偏好示范 → 通过迭代评估与分析自进化出 Skills-and-Tools Library → 得到一个可解释的 reward 系统）。Figure 1 caption 明确点出后者的产出是 "an interpretable reward system"，可解释性在这里不是副产品，而是范式转换自带的属性：库里的每一条都是一段可读的 Markdown。

值得对照的是本文选定的强对手 EditReward。它用约 20 万条偏好对做 SFT，在 Table 1 上以 Qwen 与 MiMo 两个 backbone 分别取得 42.0 与 44.1 的平均准确率，是开源阵营的最强项。RewardHarness 用其中 0.05% 的数据（约 100 条）去挑战它，这个比例本身构成了论文最有攻击性的论据。

预备知识

要读懂本文的方法，需要先明确三个概念在本文语境下的具体含义。第一个是 ranking accuracy。本文的评测不看绝对分数误差，只看候选之间的相对顺序是否与人类一致，同分记为 tie。这意味着系统输出的标量分只是排序的中间量，其绝对刻度是否校准并不进入指标。这一设定直接决定了后文自进化循环里"对/错"的判定方式。

第二个是 frozen VLM as evaluator。本文的执行者 Sub-Agent 是一个参数完全冻结的视觉语言模型（默认 Qwen2.5-VL-7B-Instruct），它的行为只由输入上下文决定。因此整套系统的"学习"发生在上下文空间而非参数空间，这也是论文标题里 post-training 一词的特殊用法：它确实发生在预训练之后，但不含任何权重更新。

第三个是 GRPO 作为下游验证手段。本文并不训练生成模型的 reward head，而是把 RewardHarness 当成一个可调用的打分函数接入 GRPO 微调流程：生成的编辑图作为唯一候选，与源图和指令一起送进系统，取回的离散分数由 GRPO trainer 在 batch 内做归一化后作为 reward。论文强调归一化方式与被对比的 reward model 完全相同，以保证 Table 2 的比较是公平的。

方法详解

问题形式化：把 reward 定义成上下文的函数

给定源图 $I_s$、编辑指令 $p$ 与 $K$ 个候选编辑图 $\{I_1,\dots,I_K\}$，系统需输出标量偏好分向量 $\mathbf{s}=(s_1,\dots,s_K)$ 以及排序 $\pi$，使得

$$I_{\pi(1)}\succ I_{\pi(2)}\succ\cdots\succ I_{\pi(K)}$$

其中 $\succ$ 表示"人类更偏好"，$\pi(j)$ 是排在第 $j$ 位的候选索引。人话：系统的任务是给一组编辑结果排出一个和人类判断一致的名次表，分数只是排名的载体。

§2.1 给出全文唯一的编号公式（1）：

$$\mathbf{s},\pi=\mathcal{M}\bigl(I_{s},\;\{I_{k}\}_{k=1}^{K},\;p,\;\mathcal{C}\bigr)$$

这里 $\mathcal{M}$ 是冻结的评估模型，$\mathcal{C}$ 是 Orchestrator 在推理时组装出来的上下文，内容为选中的 Skill 文档加 Tool 规格。人话：同一个模型 $\mathcal{M}$ 的参数永不更新，唯一会变的自变量是 $\mathcal{C}$；因此整篇论文优化的对象就是这个 $\mathcal{C}$ 的来源——库。

这个形式化有一个容易被忽略的推论：本文没有 Bradley-Terry 目标，也没有显式的 ranking loss。系统真正被优化的量是 §2.5 里的验证集排序准确率。换句话说，它的"损失函数"是一个不可微、只能通过接受/拒绝提案来搜索的离散指标。

创新点一：Library 的双类型设计（Skills 与 Tools 分离）

Library 是一个带版本的集合，初始状态为空，全部内容靠自进化长出来。它被刻意拆成两类条目，这是本文最结构性的设计决定。Skill 是一段结构化 Markdown 的评价准则，字段包括 name、one-line description、scoring rubric（把质量拆成若干可评估 criteria）与 examples；Tool 也是结构化 Markdown，但描述的是定向视觉分析流程，字段包括 name、purpose、expected inputs/outputs、invocation conditions 与 step-by-step execution protocol。

两者的区别可以用一句话概括：Skill 是 declarative 的，管"判什么"；Tool 是 procedural 的，管"怎么看"。论文给出的 Skill 例子是 realism-and-artifact-penalties，它的核心作用是区分两种不真实——视觉 artifact（一律扣分）与概念上的不真实（当指令明确要求时应当接受）。这个区分正是纯 holistic 打分最容易搞错的地方：指令要求"把猫变成宇航员"时，画面上出现不符合物理常识的元素不该被惩罚。Tool 的例子是 text-and-ocr-analyzer，负责抽取、比对与校验源图与编辑图中的文字，抓住整体印象式评估常漏掉的错字与位置错误。

Tool 的实现方式值得单独强调：它不是一个独立训练的模块，而是论文所称的 "procedural in-context specification"。通用 VLM 读过 Tool 文档后，要么临时扮演某个视觉分析专家，要么按 Tool 的 schema 发起一次结构化的二级 VLM 查询——两条路径都不需要任何参数更新。Figure 11 展示了这种 typed JSON schema 的具体形态。这一设计使得"扩展系统能力"这件事退化为"写一份新文档"，成本从训练一个模型降到生成几百 token。

创新点二：Orchestrator 的双角色与 progressive disclosure

Orchestrator 是一个基于 Claude 的 LLM，在系统里承担两个完全不同的职责。推理时它是路由器：看过指令、源图与候选图后，从库中选出合适的 Skills 与 Tools，组装成上下文 $\mathcal{C}$ 交给 Sub-Agent。这一步可以形式化为一个从任务实例到库子集的映射：

$$\mathcal{C}=\mathrm{Assemble}\bigl(\mathcal{S}_{\mathrm{sel}},\mathcal{T}_{\mathrm{sel}}\bigr),\qquad \mathcal{S}_{\mathrm{sel}}\subseteq\mathcal{S}^{(t)},\;\; \mathcal{T}_{\mathrm{sel}}\subseteq\mathcal{T}^{(t)}$$

其中 $\mathcal{S}^{(t)},\mathcal{T}^{(t)}$ 分别是第 $t$ 轮的 Skill 集合与 Tool 集合，下标 sel 表示 Router 选中的子集。人话：路由的本质是从整个库里挑出与当前这道题相关的几条，拼成一份临时的评审手册。

形式化说明：上式为按论文 §2.3 的文字描述重构的表达，论文原文未给出该编号公式。全文唯一编号公式为 §2.1 的公式 (1)。

为控制上下文长度，Tool 的加载采用 progressive disclosure：Orchestrator 起初只看到 name 与 description，只有当任务满足该 Tool 的 invocation conditions 时才加载完整 schema。这一机制解决的是一个实际工程约束——库里 Tool 的完整 protocol 通常远长于 Skill 的 rubric，若无条件全量注入，上下文预算会迅速被占满，而多数 Tool 对当前样本并不适用。

进化时 Orchestrator 换成分析者角色：拿 Sub-Agent 的推理链对照 ground truth，做 root-cause analysis，提出库的更新提案。这一角色切换是本文架构的关键——同一个强 LLM 既做路由又做诊断，但两次调用的输入完全不同，前者只看任务，后者只看失败的推理过程。

创新点三：Sub-Agent 的三步推理链

Sub-Agent 是冻结、可插拔的 VLM，默认 Qwen2.5-VL-7B-Instruct，论文同时验证了直接换成 Gemini 的情形（Table 1）。它读入 $\mathcal{C}$ 后临时变成专用评审，执行三步推理：第一步 Rubric application，对 $\mathcal{C}$ 中每个 Skill，把 rubric 逐条应用到每张候选图，产出 per-criterion 评估；第二步 Tool-guided analysis 是可选的，对满足 invocation conditions 的 Tool 按其 protocol 做定向视觉分析（OCR 抽取、空间关系校验、物体计数等），结构化结果追加到推理链；第三步 Aggregation and ranking，把所有 per-criterion 评估与 tool 输出综合成标量分 $\mathbf{s}$ 与排序 $\pi$。

Figure 2 把这条链条放进完整回路：多模态输入（源图、编辑指令、一张候选编辑图；排序任务对每个候选重复打分）进入 Orchestrator，后者从 Skills 与 Tools 库中选出相关条目，Sub-Agent 据此建立推理链输出分数与偏好判断，输出与 ground truth 比对后由 Orchestrator 分析推理链、产生更新库的 improvement signals。这条链条的价值在于它把一次整体判断拆成了可归因的若干局部判断。传统 reward model 输出一个标量，出错时无从下手；而这里每一条 criterion 的评估都留有痕迹，Orchestrator 才有可能定位"是缺了一个维度"还是"这个维度用错了"。可解释性在此不只是给人看的，它是自进化闭环能够运转的前提条件。

创新点四：自进化循环的五阶段与验证门控

输入是 $N=100$ 条人类偏好示范：

$$D=\bigl\{\bigl(I_s^{(i)},\,p^{(i)},\,\{I_k^{(i)}\},\,\mathbf{s}^{*(i)},\,\pi^{*(i)}\bigr)\bigr\}_{i=1}^{N}$$

带星号的量是人类标注的真值分与真值排序。Orchestrator 把它拆成 $D_{train}$（60 条）与 held-out 的 $D_{val}$（40 条）。人话：全部监督信号就是这 100 个例子，其中 60 个用来发现问题，40 个用来判断改动是否真的有用。

每轮迭代走五个阶段。Evaluation：对每条 train 样本检索最相关的 Skills 与 Tools，Sub-Agent 建立推理链产出 $\hat{\mathbf{s}},\hat{\pi}$。Scoring：与人类标签比对，按 ranking agreement 划分为 correct 与 error 两类，标量分差只用于诊断分析、不进入指标。Chain analysis：对错误做 root-cause 诊断，映射关系是三对一的——缺失评价维度对应新建 Skill，rubric 应用错误对应修改 Skill，感知幻觉对应新建或改进 Tool；同时也挖掘正确的推理链，识别真正起作用的条目并强化保留，最终输出结构化的 improvement proposal。Library update：只允许三种动作 create / modify / deprecate，没有 merge，另设一个 aggressive pruning 模式。Validation and gating：在 $D_{val}$ 上评估，只有优于当前最佳才接受，否则回滚。

门控准则可以形式化为在候选库上取验证准确率的最大值：

$$\mathcal{L}^{(t+1)}=\arg\max_{\mathcal{L}\in\{\mathcal{L}^{(t)},\;\mathcal{L}'\}}\;\mathrm{Acc}_{val}(\mathcal{L}),\qquad \mathrm{Acc}_{val}(\mathcal{L})=\frac{1}{|D_{val}|}\sum_{i\in D_{val}}\mathbb{1}\bigl[\hat{\pi}^{(i)}(\mathcal{L})=\pi^{*(i)}\bigr]$$

其中 $\mathcal{L}^{(t)}$ 是第 $t$ 轮的当前库，$\mathcal{L}'$ 是应用了本轮提案后的候选库，$\mathbb{1}[\cdot]$ 是指示函数。人话：每轮改完先在 40 条留出集上考一次，考得更高就留下，否则整批改动撤销。

形式化说明：以上两式为按论文 §2.5 的文字流程重构的表达，论文原文未给出编号公式，也未提供 Algorithm 伪代码块（全文未出现 "Algorithm"）。

停止条件是固定迭代预算，而非收敛判据——这一点论文写得很明确。实际跑满 77 轮，最终选出并冻结的是 best-validation library，即 iteration 69 的状态。这个设定意味着 77 这个数字没有理论含义，它只是预算。

创新点五：下游 GRPO 的接入方式

把 RewardHarness 接进 GRPO 时，生成的编辑图作为唯一候选，与源图和指令一起送入系统打分，得到的离散分数由 trainer 在 batch 内做归一化后作为 reward。这一步可写作：

$$r_i=\frac{s_i-\mu_B}{\sigma_B+\epsilon},\qquad \mu_B=\frac{1}{|B|}\sum_{j\in B}s_j$$

其中 $B$ 是一个 batch（GRPO 中的一组 rollout），$\mu_B,\sigma_B$ 是组内均值与标准差，$\epsilon$ 为数值稳定项。人话：绝对分数刻度被消掉，只有"这一张比同组其他张好多少"进入梯度，这也解释了为什么系统只要排序对就够用。

形式化说明：本式为按论文对 GRPO batch 归一化的文字描述重构的标准形式，论文原文未给出该公式；论文仅说明归一化方式与被对比的 reward model 相同。

方法与源码的对应关系

仓库已公开且结构完整：src/ 下有 pipeline.py、router.py、evaluator.py、evolver.py、chain_analyzer.py、sub_agent.py、gemini_client.py、endpoint_pool.py，以及签入的 library_gemini_v1 至 v5；scripts/ 提供 run_evolution.py、run_benchmark.py、reproduce.sh、vLLM 启动脚本与 check_env.py；tests/ 有约 107 个测试且不需要 GPU 与网络。文件名与论文模块几乎一一对应：router.py 对应 §2.3 的 Router，chain_analyzer.py 对应 §2.5 的 Chain analysis。

第一处实质对应在配置文件。configs/default.yaml：

evolution:
  train_dataset: AgPerry/EditReward-Data-100
  train_n: 60
  val_n: 40
  max_iterations: 5
  batch_concurrent: 128
  explore_margin: 0.075
  augment_swap: true
  prune_every_n: 50
  seed: 42

train_n: 60 与 val_n: 40 精确对应 §2.5 的 60/40 拆分，数据集名 AgPerry/EditReward-Data-100 对应 $N=100$ 的校准集。prune_every_n: 50 与论文"约第 50 轮开始剪枝"的描述吻合。augment_swap: true 对应候选顺序交换，用来对抗位置偏置——这与库中 objective-visual-description-first 这条 Skill 在治同一个病，一个从数据侧、一个从提示侧。

第二处对应在 src/evolver.py，它把 §2.5 的三种动作落成了字面上的三个分支：

applied = {"skills_added": 0, "skills_updated": 0, "skills_deleted": 0,
           "tools_added": 0, "tools_updated": 0, "tools_deleted": 0}
for u in signals.get("skill_updates", []):
    if u["action"] == "add":    self.library.add_skill(...)
    elif u["action"] == "update": self.library.update_skill(...)
    elif u["action"] == "delete": self.library.delete_skill(u["name"])

该模块的 docstring 写着："Applies improvement signals to Library (add/update Skills and Tools). Supports snapshot/restore for rollback on val_acc regression." add / update / delete 三分支即论文的 create / modify / deprecate，snapshot/restore 即验证门控失败时的回滚，回滚判据明确写成 val_acc regression。论文里抽象描述的门控在代码里是一个具体的快照恢复操作，两者对得上，这提高了方法描述的可信度。

实验分析

进化轨迹：准确率与库规模的非单调关系

自进化过程本身是本文最有信息量的实验。空 library 的 baseline 为 42.5%；库长到 13 条时进入 plateau，停在 52.5%；iteration 69 达到 62.5%，相对空库提升 47%。被接受的更新集中在很窄的几个窗口：iters 5–7、10、58–60。这意味着 77 轮里绝大多数轮次的提案都被门控拒绝，进化不是平滑爬坡而是长时间停滞后的少数跃迁。

库规模的轨迹与准确率并不同向。初始 0 条，iter 10 增到 9 条（6 Skills + 3 Tools），iter 49 达到峰值 13 条（8 Skills + 5 Tools），约 iter 50 起开始剪枝，iter 69 收敛到 7 条（3 Skills + 4 Tools）。也就是说，最好的库比中途的最大库少了 6 条，而准确率从 52.5% 涨到了 62.5%。剪枝阶段贡献了最后 10 个百分点，这与"条目越多能力越强"的直觉相反：条目之间会互相干扰，冗余的 rubric 会稀释 Sub-Agent 对关键维度的注意力。

另一个细节在论文原文中被点出："many proposed updates were rolled back, and Skill proposals were accepted less often than Tool proposals." Skill 提案的接受率低于 Tool 提案，且最终库里 Tool（4 条）多于 Skill（3 条）。合理的解释是：Skill 修改的是全局评分标准，牵一发动全身，在 40 条验证集上更容易造成局部回退；而 Tool 只在满足 invocation conditions 时才被触发，作用域窄，副作用小，因此更容易通过门控。这也解释了为什么感知类问题（OCR、计数、空间关系）更适合用 Tool 而不是 Skill 来治。

讨论

方法的适用边界由它的机制决定。整套系统只有在两个条件同时成立时才有效：一是失败必须可归因，Sub-Agent 的推理链要足够结构化，Orchestrator 才能定位是维度缺失还是应用错误；二是评价标准必须能被自然语言写清。图像编辑刚好满足这两点。若换成一个人类自己也说不清标准的任务（例如审美偏好的细微差异），chain analysis 会失去着力点，此时"上下文进化"退化为盲搜。

论文在结论里把这件事表述为一个新的扩展轴："More broadly, these results suggest a complementary scaling axis for reward modeling: explicit evaluation context." 这个提法没有否定参数扩展，而是提出显式评价上下文是与之互补的第二根轴。从 Table 1 中 Qwen 32B 反低于 7B 的现象看，在评价任务上第二根轴的边际收益可能确实更高。

但资料中存在两处需要读者注意的不一致，都与实现细节相关。第一处是 rubric 刻度：论文 §2.1 明确写实现为 1–5 的离散 rubric，而开源仓库 README 描述产出的是 "1–4 preference judgment"，目录注释也写着 score-guidelines/ # 1–4 scoring rubric templates。1–5 与 1–4 的差别不只是刻度长短：奇数刻度有中间档，偶数刻度强制评审在偏好上表态。这会影响 tie 的产生频率，进而影响 ranking accuracy 的统计，也会影响 GRPO 归一化后 reward 的方差。论文正文与开源代码在这一点上无法同时为真，复现者需要先确认自己用的是哪一套。

第二处是迭代预算：论文跑了 77 轮并取 iteration 69 的库，而 configs/default.yaml 里 max_iterations: 5。按默认配置直接运行 scripts/run_evolution.py，进化会在第 5 轮停止，落在论文所述"iters 5–7 被接受"窗口的最开头，几乎不可能重现 62.5% 的验证准确率。更微妙的是 prune_every_n: 50 在 5 轮预算下永远不会触发，而剪枝阶段恰恰贡献了从 52.5% 到 62.5% 的关键提升。这个默认值大概率是为快速冒烟测试而设，但它与论文实验配置的落差需要在文档中显式说明，否则开源仓库的默认行为会系统性低估方法效果。

未解决的问题还有一个方法论层面的：由于停止条件是固定预算而非收敛判据，77 与 69 这两个数字都不具备可迁移性。换一个任务或换一个 Sub-Agent，需要多少轮、在哪一轮达到峰值，本文没有提供任何预测依据，只能靠重新烧一遍预算试出来。

局限分析

作者自述之一：Orchestrator 对闭源模型的依赖。原文写："The Orchestrator currently relies on a proprietary LLM (Claude) for routing, chain analysis, and library evolution… This coupling limits full reproducibility and introduces a dependency on API availability and cost." 这一点与本文的卖点形成张力：论文的核心论据之一是传统范式无法作用于闭源模型，而它自己的进化引擎恰恰依赖闭源模型。两者并不矛盾——被评估的 Sub-Agent 可以是开源冻结模型，闭源依赖只在进化阶段——但这意味着"零训练成本"的说法需要限定：省掉的是 GPU 训练，付出的是 77 轮 Orchestrator API 调用。论文未提供成本分析表，这笔账的绝对数额无法核算。

作者自述之二：门控不保证全局最优。原文写："The conservative rollback gate reduces regressions, but it does not guarantee discovery of globally optimal Skills or Tools; useful proposals may be rejected when they help rare cases but slightly hurt frequent ones." 这是贪心搜索的固有代价，并且与 Skill 提案接受率低于 Tool 的观察互为印证：改动作用域越大，越容易在频繁样本上造成轻微回退而被整批拒绝。论文同时承认第三点局限：系统目前限于单模态单任务，且 40 条验证集过小，带来过度专化风险。项目页进一步补充："Skill plateaus… The library converges to a compact 7-entry final state after pruning, which may hide longer-tail failure modes the calibration set never surfaces."

独立判断之一：40 条验证集与 62.5% 的可信度。验证准确率的每一步都以 1/40 = 2.5 个百分点为最小刻度，而报告的三个数字 42.5%、52.5%、62.5% 全部落在 2.5% 的整数倍上，分别对应 17、21、25 条正确。用 25 条正确判定一个库优于另一个库，采纳与回滚决策的信噪比很低；在 77 轮里反复用同一个 $D_{val}$ 做选择，等价于对这 40 条做了多重比较，best-validation 的选点必然带有乐观偏差。Table 1 上 47.4% 的测试结果低于验证集的 62.5%，与这一分析方向一致（两者基准集不同，不能直接相减，但差距的方向值得记住）。

独立判断之二：下游收益的规模与稳健性未被充分刻画。Table 2 的 Overall 优势为 3.52 对 3.45，仅 0.07；而 Remove 一列出现 0.71 的回退。在没有多种子重复、没有置信区间、也没有消融实验的情况下，很难区分这 0.07 是方法优势还是单次运行的波动。此外全部下游实验绑定在 FLUX.2-klein-base-4B 这一个 backbone 上，reward 的偏好结构会不会在更大的生成器上呈现不同的传导模式，本文没有回答。

结论

本文的贡献可以凝练成三句。第一，它给出了一个把 reward modeling 从权重优化改写为上下文进化的完整可运行系统：100 条人类偏好示范加一个参数冻结的 VLM，在图像编辑评测上取得 47.4% 的平均排序准确率，比 GPT-5 高 5.3 分，用掉的偏好数据是 EditReward 的 0.05%。第二，它把 Skills（declarative，判什么）与 Tools（procedural，怎么看）分离，配合 progressive disclosure 与 create/modify/deprecate 三动作加验证回滚的门控，使自进化在只有 40 条留出样本的条件下不至于失控。第三，它验证了这套系统可以直接当作 GRPO 的 reward 接入下游，把 4B backbone 从 3.32 抬到 3.52，超过用 20 万偏好对训练的监督 reward baseline。

更有延展性的是论文结论里那句判断：显式的评价上下文构成了 reward modeling 的一条互补扩展轴。Table 3 只有 7 条人类可读的条目，却承担了传统范式中 20 万条标注的角色，而进化轨迹中"从 13 条剪到 7 条反而涨 10 个点"的现象，说明这条轴上的关键变量不是条目数量而是条目质量与彼此的正交性。论文列出的未来方向包括换用开源 LLM 做 Orchestrator、扩展到 text-to-image 质量评估与视频编辑及 3D 场景操作、以及给验证门控加入 diversity-aware sampling、不确定性估计或轻量人工审计（用于争议与安全敏感领域）。其中第一项直接对应最主要的局限，第三项则对应 40 条验证集带来的选点偏差——这两项能否被解决，决定了这条新扩展轴能走多远。
