一、先看一个不太合理的对比

你手里有两个学生，要考同一门课：给一张原图、一句修图指令、几张修完的图，判断哪张改得更好。

甲同学的复习方式是刷题：二十万对人类偏好比较，一条条喂进去做 SFT，练出一个专门打分的模型。乙同学只看了 100 条示范，然后开始自己给自己写笔记、写检查清单，反复推敲了 77 遍。

你猜谁赢了？RewardHarness 这篇论文里，乙赢了。它在图像编辑评测上拿到 47.4% 的平均排序准确率，比 GPT-5 高 5.3 分，而它用掉的偏好数据是 EditReward 那套的 0.05%。

0.05% 是个什么概念？别人抄了两千页题库，你只翻了一页，考得还更好。而且乙同学全程一个参数都没动过——它的模型权重是冻结的。

一句话版本

把"训一个奖励模型"改成"给一个通用视觉模型攒一套评审手册"，手册由 100 条人类示范自己迭代长出来，模型权重全程不动。

二、为什么以前非得那么干？

先说清楚"奖励模型"（reward model）是干什么的。说白了，它就是个打分员：你要让生图模型学会人类喜欢什么，得先有个东西能替人类说"这张好、那张差"，RL 才有方向。

过去的标准流水线是三步：收集大规模人类偏好标注 → SFT 训练一个专用奖励模型 → 拿它当 reward 信号做 RL 对齐。这套路子跑了好几年，工程上很成熟。

但它有四个绕不开的坑，论文在动机部分点得很直：标注成本高；必须额外训练一遍；输出是一个不透明的标量分（scalar reward），你没法问它"你为什么给 3 分"；最后一条最扎心——它对闭源、只给 API 的基础模型完全没辙，因为你没法微调别人的权重。

图像编辑这个场景把这些坑都放大了。判一张编辑图好不好，你得同时看三样东西：编辑指令、源图、编辑结果。偏好又细又多维——文字有没有拼错、物体数对不对、背景换了前景有没有塌、艺术风格是不是那个风格。

这就是论文摘要里点名的那个缺口：

"This creates a data-efficiency gap: humans can often infer the target evaluation criteria from only a few examples, while models are usually trained on hundreds of thousands of comparisons."

你想想自己第一次当评委的经历。别人给你看五个例子、讲一遍评分要点，你基本就知道该看什么了。人类靠的不是把二十万个样本背进脑子，而是提炼出一份评分标准。

三、核心洞察：奖励建模不一定要动权重

论文的那句关键话是：把奖励建模重新定义为"上下文进化"（context evolution），而不是"权重优化"。

知识不一定要压进参数里，它可以就明明白白写在上下文里。以前你想让模型变强只有一条路——改它的脑子；这篇论文走的是另一条路——不改脑子，改它手边那本工作手册。就像你不给新来的审稿人做开颅手术，你给他一份评审细则和几张检查表，他当天就能上岗。

四、它到底怎么做的

第 0 步：把打分这件事写成一个函数

给一张源图 $I_s$、一句编辑指令 $p$、K 张候选编辑图 $\{I_1,\dots,I_K\}$，系统要输出一组标量分 $\mathbf{s}=(s_1,\dots,s_K)$ 和一个排序 $\pi$，满足 $I_{\pi(1)}\succ I_{\pi(2)}\succ\cdots\succ I_{\pi(K)}$。全文 §2.1 里唯一那个编号公式长这样：

$$\mathbf{s},\pi=\mathcal{M}\bigl(I_{s},\;\{I_{k}\}_{k=1}^{K},\;p,\;\mathcal{C}\bigr)$$

人话解释：$\mathcal{M}$ 是那个通用视觉模型，$\mathcal{C}$ 是推理时临时组装进去的"评审手册"。这个公式里没有任何可学参数——$\mathcal{M}$ 的参数永不更新，唯一会变的是 $\mathcal{C}$。这也是为什么这篇论文没有 Bradley-Terry、没有显式 ranking loss：它的"目标函数"实际上就是验证集上的排序准确率。

分数是 1–5 的序数质量估计，评测只看相对顺序，同分算 tie。这里有个小细节值得挑出来：论文写的是 1–5，但开源仓库 README 说产出的是 "1–4 preference judgment"，目录也明明白白写着 score-guidelines/ # 1–4 scoring rubric templates。论文和代码在这一点上没对齐。

第 1 步：Library —— 一本从零页开始的手册

系统的全部"知识"都装在一个带版本的 Library 里，里面只有两类东西：Skill 和 Tool。而这个 Library 初始是空的，一条都没有。

Skill 是结构化 Markdown 写的评价准则，字段包括 name、一句话描述、scoring rubric（把质量拆成可评估的 criteria）、examples。比如 realism-and-artifact-penalties 这条，专门区分两种"不真实"：视觉 artifact 一律扣分，但概念上的不真实——如果指令明确要求（比如"把猫变成宇航员"）——是可以接受的。

Tool 是结构化 Markdown 写的定向视觉分析流程，字段包括 name、purpose、输入输出、调用条件、逐步执行协议。注意 Tool 不是独立训练的模块，它是一份 "procedural in-context specification"：通用 VLM 读完这份文档，就能临时扮演某个视觉分析专家，或者按 Tool 的 schema 发起一次结构化的二级 VLM 查询，全程不需要任何参数更新。

比如 text-and-ocr-analyzer：抽取并比对源图和编辑图里的文字，专抓整体印象式评估最容易漏掉的错字和位置错误。

一句话记住两者的分工：Skill 是声明式的（判什么），Tool 是过程式的（怎么看）。前者是评分表，后者是量尺。

第 2 步：Orchestrator —— 既当调度员又当教研组长

Orchestrator 是一个基于 Claude 的 LLM，兼两份工。

推理时它是调度员：看完指令、源图、候选图，通过 Router 选出该用哪些 Skill 和 Tool，组装成上下文 $\mathcal{C}$ 交给 Sub-Agent。为了不把上下文撑爆，Tool 用了 progressive disclosure（渐进披露）：先只让它看 name + description，只有满足调用条件才加载完整 schema。

这招像什么？像一个工具箱的抽屉都贴着标签，你先扫标签，确定要用扳手才把那格拉开——不用把整箱工具全倒在桌上。

进化时它是教研组长：拿 Sub-Agent 的推理链（reasoning chain）对照标准答案，做 root-cause 分析，写出一份该怎么改手册的提案。

第 3 步：Sub-Agent —— 一个可换的、冻结的评审

Sub-Agent 是一个冻结的、可插拔的 VLM，默认用 Qwen2.5-VL-7B-Instruct，论文也验证了直接换成 Gemini 一样能跑（Table 1）。它读完 $\mathcal{C}$ 里的手册，就临时变成一个专用评审，走三步推理链：

一，Rubric application：把 $\mathcal{C}$ 里每个 Skill 的 rubric 逐条应用到每张候选图，产出 per-criterion 评估。二，Tool-guided analysis（可选）：满足调用条件的 Tool 按各自协议做定向分析——OCR 抽取、空间关系校验、物体计数——结构化结果追加到推理链里。三，Aggregation and ranking：把所有分项评估和工具输出汇总成 $\mathbf{s}$ 和 $\pi$。

你注意这个结构的妙处：换 Sub-Agent 不用重训手册，换手册不用重训 Sub-Agent。两边解耦了。

第 4 步：自进化循环 —— 77 轮的自我批改

这是全篇最核心的机制。输入只有 N=100 条人类偏好示范 $D=\{(I_s^{(i)},p^{(i)},\{I_k^{(i)}\},\mathbf{s}^{*(i)},\pi^{*(i)})\}_{i=1}^{N}$，Orchestrator 自己把它拆成 60 条训练、40 条留出验证。

然后每一轮跑五个阶段：Evaluation（检索最相关的条目，Sub-Agent 出分）→ Scoring（按排序一致性划成 correct / error，标量分差只用来做诊断）→ Chain analysis（对错误做根因诊断）→ Library update → Validation and gating。

Chain analysis 那一步有个很干净的三对一映射，值得单独记：缺失评价维度 → 新建 Skill；rubric 应用错了 → 改 Skill；感知幻觉 → 新建或改进 Tool。同时它也会去挖那些答对的推理链，把真正起作用的条目识别出来强化保留。

Library 的更新动作只有三种：create / modify / deprecate——没有 merge。另外还有一个 aggressive pruning 模式，负责把冗余条目砍掉。

最后一道闸门是最关键的：新手册要在那 40 条验证集上评一遍，只有比当前最好成绩更好才被接受，否则整个更新回滚。论文原文说得很实在：

"many proposed updates were rolled back, and Skill proposals were accepted less often than Tool proposals."

这套流程像什么？像一个考生每次模考完都要做错题本，但他有个铁规矩：新总结的方法必须在另外 40 道从没见过的题上考得更好，才准写进错题本，否则当场撕掉。

停止条件不是收敛判据，就是一个固定的迭代预算。论文一共跑了 77 轮，最后挑出验证集最优的那一版并冻结——iteration 69。

第 5 步：手册长胖又变瘦的曲线

准确率轨迹是这样的：空手册基线 42.5% → 长到 13 条时在 52.5% 卡住（plateau）→ iter 69 冲到 62.5%，相对提升 47%。被接受的更新集中在几个很窄的窗口：iters 5–7、10、58–60。

规模轨迹更有意思：从 0 条起步 → iter 10 变成 6 skills + 3 tools（9 条）→ iter 49 涨到峰值 13 条（8 Skills + 5 Tools）→ 约第 50 轮开始剪枝 → iter 69 收成 7 条（3 Skills + 4 Tools）。

先长胖再瘦身，最后工具比技能还多。这说明什么？说明后期的收益不是来自"想出更多评分维度"，而是来自"给模型配更靠谱的眼睛"。看不准比想不到更致命。

第 8 步：论文说的和代码写的，对得上吗

我去翻了仓库，两处对应关系挺硬。第一处是 configs/default.yaml：

evolution:
  train_dataset: AgPerry/EditReward-Data-100
  train_n: 60
  val_n: 40
  max_iterations: 5
  batch_concurrent: 128
  explore_margin: 0.075
  augment_swap: true
  prune_every_n: 50
  seed: 42

train_n: 60 / val_n: 40 和论文 §2.5 的 60/40 拆分完全一致，数据集名字 EditReward-Data-100 就是那个 N=100 校准集。prune_every_n: 50 正好对上论文"约第 50 轮开始剪枝"。augment_swap 是把候选顺序交换以对抗位置偏置——和 objective-visual-description-first 那条 Skill 治的是同一个病。唯一对不上的是 max_iterations 默认只有 5，论文跑了 77。

第二处是 src/evolver.py：

applied = {"skills_added": 0, "skills_updated": 0, "skills_deleted": 0,
           "tools_added": 0, "tools_updated": 0, "tools_deleted": 0}
for u in signals.get("skill_updates", []):

六、这件事的意义比一个 SOTA 大

技术上，它给奖励建模拆出了一条新的扩展轴。论文结论里那句话我觉得是全篇最有分量的：

"More broadly, these results suggest a complementary scaling axis for reward modeling: explicit evaluation context."

过去我们扩的是参数量和数据量，这里扩的是写清楚的评价上下文。这两条轴不冲突，可以叠加。

产业上，它把奖励模型的门槛从"你有没有标注团队和训练集群"改成了"你有没有 100 条高质量示范和一个 API key"。对绝大多数团队来说，这两件事的难度差了几个数量级。而且因为不碰权重，闭源基座第一次能直接当奖励模型的地基用。

方法学上，我觉得最值得抄的其实不是 Skill / Tool 这套设计，而是那道验证门控。让模型自我改进的尝试遍地都是，绝大多数死在"越改越差还不知道"。这篇论文的做法很朴素：留 40 条不给看，改完必须在这 40 条上更好，不然就回滚。自进化系统缺的从来不是创造力，是刹车。

七、别忽略这些坑

作者自己在 §5 里挑明了第一条，也是最要命的一条——Orchestrator 依赖闭源模型：

"The Orchestrator currently relies on a proprietary LLM (Claude) for routing, chain analysis, and library evolution… This coupling limits full reproducibility and introduces a dependency on API availability and cost."

换句话说，那个又当调度员又当教研组长的大脑，是租来的。这直接影响可复现性，也把成本和可用性绑在了别人的 API 上。第二条作者自述是门控机制本身的代价：

"The conservative rollback gate reduces regressions, but it does not guarantee discovery of globally optimal Skills or Tools; useful proposals may be rejected when they help rare cases but slightly hurt frequent ones."

刹车踩得太稳，就会把那些"救了长尾但轻微拖累主流"的好想法一起否掉。作者还提到第三点：目前只做了单模态单任务，40 条验证集偏小，有过度专化的风险。项目页补了一句更实在的：最终收成 7 条的紧凑 library，"may hide longer-tail failure modes the calibration set never surfaces"。

我自己再补两点判断。一是那个 1–5 还是 1–4 的矛盾：论文写 1–5，仓库 README 和 score-guidelines/ 写 1–4，这不是笔误级别的小事——如果实际跑的是 1–4，rubric 的粒度和论文描述就有偏差，想复现的人得先自己确认一遍。二是准确率轨迹的可疑之处：77 轮里被接受的更新只集中在 iters 5–7、10、58–60 这几个窗口，中间几十轮几乎没进展。62.5% 出现在 iter 69，而 iter 49 峰值 13 条时只有 52.5% 一线，这条曲线在 40 条验证集上的方差有多大，论文没给（也没有消融实验能帮你判断是哪个条目在起作用）。

八、回到开头那两个学生

甲同学刷了二十万道题，考了 42.0。乙同学看了 100 道题，写了 77 版错题本，扔掉一半，最后留下 7 条，考了 47.4。

但真正的差别不在分数。你去问甲"你为什么给这张图打 3 分"，它给不出答案，它只有一个数。你去问乙，它会告诉你：先客观描述了三张图，然后调了 OCR 工具发现第二张的招牌文字拼错了，所以扣分。

而且乙的错题本是一份 Markdown。你能读、能改、能自己往里加一条、能拿去给另一个模型用。它不是压在几十亿参数里的一团权重，它是写下来的东西。

这大概才是这篇论文真正在问的问题：我们让模型变强的时候，有多少次是因为真的必须动它的脑子，又有多少次只是因为我们懒得把标准写清楚？

别再急着教模型你的偏好——先把它写下来，写清楚的标准比训进去的权重跑得更远。
