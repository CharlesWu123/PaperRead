核心摘要

做什么：给指令式图像编辑做偏好评分与排序，但不训练任何 reward model 权重。
怎么做：把 reward modeling 重构为 context evolution——Orchestrator 从 100 条人类示范里迭代进化出一个 Skills + Tools 库，推理时组装成上下文喂给冻结的 VLM Sub-Agent。
效果：仅用 EditReward 偏好数据的 0.05%，在图像编辑评测上取得 47.4% 平均排序准确率，超过 GPT-5 5.3 分；作为 GRPO 的 reward 信号把 FLUX.2-klein-base-4B 从 3.32 抬到 ImgEdit-Bench 3.52。
适用场景：标注预算极小、需要可解释评分理由、或基础模型只有 API 无法微调的对齐任务。

问题在哪

现行路线是"收集大规模人类偏好标注 → SFT 训练专用 reward model → 用于 RL 对齐"。论文点了它四处痛：标注成本高、必须额外训练、输出是不透明的 scalar reward、对闭源或仅 API 的基础模型完全用不上。图像编辑把这些放大了——判断需要同时理解编辑指令、源图和编辑结果，偏好细微且多维。

"humans can often infer the target evaluation criteria from only a few examples, while models are usually trained on hundreds of thousands of comparisons."

这就是论文所称的 data-efficiency gap，也是全篇的出发点。

方法形式化

给定源图 $I_s$、编辑指令 $p$、$K$ 个候选编辑图 $\{I_1,\dots,I_K\}$，系统输出标量偏好分 $\mathbf{s}=(s_1,\dots,s_K)$ 与排序 $\pi$，满足 $I_{\pi(1)}\succ I_{\pi(2)}\succ\cdots\succ I_{\pi(K)}$：

$$\mathbf{s},\pi=\mathcal{M}\bigl(I_{s},\;\{I_{k}\}_{k=1}^{K},\;p,\;\mathcal{C}\bigr)$$

关键在 $\mathcal{C}$：Orchestrator 在推理时组装的 Skill 文档加 Tool 规格；$\mathcal{M}$ 的参数永不更新。这是 §2.1 唯一的编号公式——论文没有 Bradley-Terry 建模，也没有显式 ranking loss，真正被优化的"目标函数"是 §2.5 里那个验证集 ranking accuracy。分数是与人类示范同一离散 rubric 上的序数估计（论文写 1–5），只用相对顺序计算准确率，同分算 tie。下游 GRPO 里，生成的编辑图作为唯一候选连同源图与指令一起打分，1–5 分由 trainer 做 batch 归一化后作为 reward，归一化方式与被对比的 reward model 完全一致。

关键创新

1. 用 context evolution 替代 weight optimization

核心是把"学一个打分器"换成"长一套评价标准"。系统从空库出发，靠 100 条示范迭代生成、修改、废弃 Skill 与 Tool 条目，基础模型参数一次不动。重要性在于它解绑了 reward 质量与标注规模的关系，也让闭源 API 模型第一次能直接充当 reward 主体。

2. Skill / Tool 的声明式与过程式分工

Skill 是结构化 Markdown 的评价准则（name、一句话描述、scoring rubric、examples），管"判什么"，例如 realism-and-artifact-penalties 明确区分"视觉 artifact 一律扣分"与"指令要求时可接受的概念性不真实"。Tool 是定向视觉分析流程（purpose、输入输出、invocation conditions、step-by-step protocol），管"怎么看"，例如 text-and-ocr-analyzer 抽取并比对两图文字。Tool 不是独立训练的模块，而是 procedural in-context specification：通用 VLM 读完文档就能临时扮演某类视觉专家，或按 Tool 的 typed JSON schema（Figure 11）发起一次二级 VLM 查询，零参数更新。这套分工把"评价标准"和"感知手段"的失败原因分开，才让后面的 root-cause 归因可行。

3. 带回滚门控的五阶段自进化循环

每轮走 Evaluation → Scoring → Chain analysis → Library update → Validation and gating。诊断有固定三映射：缺失评价维度就新建 Skill、rubric 应用错误就修改 Skill、感知幻觉就新建或改进 Tool；同时挖掘正确推理链，把起作用的条目强化保留。更新只有 create / modify / deprecate 三种动作（没有 merge），另有 aggressive pruning 模式；在 40 条 held-out 上优于当前最佳才接受，否则回滚。作者坦言"many proposed updates were rolled back, and Skill proposals were accepted less often than Tool proposals"——这也解释了最终库里工具比技能多。

4. 两级架构 + progressive disclosure 控上下文

Orchestrator（Claude）负责推理时路由与进化时归因，Sub-Agent 是冻结、可插拔的 VLM，默认 Qwen2.5-VL-7B-Instruct，Table 1 也验证了直接换成 Gemini。Sub-Agent 走三步推理链：逐条应用 rubric → 对满足 invocation conditions 的 Tool 做定向分析（OCR 抽取、空间关系校验、物体计数）→ 聚合为 $\mathbf{s}$ 与 $\pi$。为压上下文长度，Tool 先只暴露 name 与 description，命中调用条件才加载完整 schema。可插拔性意味着评价能力沉淀在库里而非某个 backbone 里。

论文方法 ↔ 源码对应

仓库已公开（Apache-2.0），src/ 下是 pipeline.py、router.py、evaluator.py、evolver.py、chain_analyzer.py、sub_agent.py、gemini_client.py、endpoint_pool.py，并签入了 library_gemini_v1…v5；tests/ 约 107 个测试，不需 GPU 或网络。第一处对应在 configs/default.yaml：

evolution:
  train_dataset: AgPerry/EditReward-Data-100
  train_n: 60
  val_n: 40
  max_iterations: 5
  batch_concurrent: 128
  explore_margin: 0.075
  augment_swap: true
  prune_every_n: 50
  seed: 42

train_n=60 / val_n=40 与 §2.5 的拆分一致，数据集名直指 N=100 校准集，prune_every_n: 50 对上"约第 50 轮开始剪枝"，augment_swap 是候选顺序交换以对抗位置偏置——与 objective-visual-description-first 治的是同一个病。落差在 max_iterations 默认只有 5，论文跑了 77 轮，复现要自己调。第二处对应在 src/evolver.py：

applied = {"skills_added": 0, "skills_updated": 0, "skills_deleted": 0,
           "tools_added": 0, "tools_updated": 0, "tools_deleted": 0}
for u in signals.get("skill_updates", []):
    if u["action"] == "add":      self.library.add_skill(...)
    elif u["action"] == "update": self.library.update_skill(...)
    elif u["action"] == "delete": self.library.delete_skill(u["name"])

三个 action 严格对应 create / modify / deprecate，docstring 也写明 "Supports snapshot/restore for rollback on val_acc regression"，就是论文的验证门控。

局限

作者自述：Orchestrator 依赖闭源 Claude 做路由、链分析与库进化，"This coupling limits full reproducibility and introduces a dependency on API availability and cost"；保守回滚门控降低了回归，但"does not guarantee discovery of globally optimal Skills or Tools"——对罕见情形有益、对常见情形略有损害的提案会被误杀。此外是单模态单任务，40 条验证集太小，有过度专化风险；项目页补充剪枝后收敛到 7 条紧凑状态"may hide longer-tail failure modes the calibration set never surfaces"。

我的判断：其一，rubric 刻度对不齐——论文写 1–5，开源 README 写 "1–4 preference judgment"，目录也是 score-guidelines/ # 1–4 scoring rubric templates；这直接影响分数分布与 GRPO 归一化后的 reward 尺度，复现前必须确认。其二，77 轮里真正被接受的更新只集中在三个窄窗口，62.5% 的最优点又是在同一个 40 条集合上挑出来的，"best-validation library = iteration 69"存在明显的选择偏差，泛化增益里有多少来自真实标准、多少来自校准集拟合无从判断。其三，论文没有消融表、没有数据效率对比表、也没有成本与延迟分析，而这套方案每次评分都要多次 LLM 与二级 VLM 调用——把 API 成本折进来后，"数据效率高"是否等于"总体更省"仍是开放问题。

结论

100 条标注加一个冻结 VLM，换来 47.4% 平均准确率和优于有监督 reward baseline 的下游 RL 效果。论文的落点不是刷榜，而是提出一条被忽视的扩展轴：

"More broadly, these results suggest a complementary scaling axis for reward modeling: explicit evaluation context."

未来工作写在 §5 内：换开源 LLM 做 Orchestrator，扩展到 text-to-image 质量评估、视频编辑、3D 场景操作，并给验证门控加 diversity-aware sampling、不确定性估计或轻量人工审计。

偏好不一定要压进权重里——写清楚，也是一种对齐。
