# 通俗版 · HarnessDev：考一考大模型能不能自己造「agent 的驾驶舱」，结果一半进步是错觉

> 一个新基准让 6 个大模型从零造 agent 外壳、再拿真实评测反馈去养它，共 2207 个任务、73 个版本；结论：造得出但比人类工程差一截，演化时「看得见的涨分」和「看不见的考分」方向一致的次数只有约一半。

## 一分钟版本

- 模型权重全程不动，考的是「写代码造 agent 外壳」的能力：从只有一个能跑但什么都不干的种子开始，写出一个完整的执行系统。
- 六个模型参赛，四个领域五个基准。最强的 Opus 4.8 平均 67.8 分，人类成熟工程参照是 86.2 分——写作和机器学习实验两项追平甚至反超，代码和搜索差距很大。
- 加的代码多少跟成绩无关：全场加码最少的 Gemini（1,006 行）拿下终端基准最高分（68.8）。
- 第二阶段让模型继续养自己造的代码 harness：9 条演化血统、73 个官方版本。看得见的反馈分数全在涨，但换到 630 个从未见过的任务上，64 次版本切换只有 34 次方向一致；9 个「最终交付版」只有 2 个是真正最优。
- 固定用 Gemini 当执行模型的消融更狠：4 条血统里 3 条在未见任务上倒退，最多倒退 10.32 分——很多「进步」是专门伺候自己熟的那个模型的。
- 反作弊审计全程零违规；但状态管理和验证是系统性盲区——26,679 条任务轨迹里一次「保存状态」都没发生过。

## 先搞清楚几个概念

**什么是 harness。** 大模型是发动机，harness 是整个驾驶舱：执行循环（什么时候继续、什么时候停）、工具（能用什么）、上下文（往 context 里塞什么）、状态与记忆（记不记得之前干过什么）、生命周期（出错后怎么恢复）、验证（怎么确认活干对了）。它的影响力大到什么程度：同一个 GPT-5，放在 Terminus 2 里 Terminal-Bench 2.1 考 35.2%，放在 Codex CLI 里考 49.6%——一个字都没改，14 分的差距全来自外壳。

**创建 vs 演化。** 这篇论文把「develop a harness」拆成两步：Creation 是从零造——给你一个只解析任务、写写日志、啥也不干的种子兼容层，造一个能干活的完整系统；Evolution 是持续维护——拿你自己造好的那个 harness，凭真实评测反馈一轮一轮改代码，像养一个长期项目。注意演化阶段不给任何标准答案，模型只能看「这 100 个 SWE 任务 + 89 个终端任务跑了几分」这种真实成绩单。

**visible feedback vs held-out。** 演化时模型能看到 189 个任务的分数，这叫可见反馈；另有 630 个 SWE 任务专门留到最后考，分数从头到尾不给模型看，这叫 held-out。整篇论文最有价值的对照就是：**你看得见的分数涨了，看不见的那份涨没涨？**（跟学生刷题册子上的分数和期末闭卷考的关系类似。）

**creator vs executor。** 写 harness 的模型和被塞进 harness 里干活的模型是两个角色。默认是同一个人（自己写自己用）；消融实验里把干活的角色换成固定的 Gemini，看写出来的外壳是「通用工程」还是「只伺候熟人」。顺带一提：写代码这件事本身是在真实开发环境里做的——六个模型统一在 Claude Code 2.1.177 里干活（GPT-5.5 例外，用 Codex），像程序员一样读文档、改文件、跑自测，最后交一份能跑的工程。

## 它想解决什么问题

现在所有 agent 评测都是：选一个现成 harness（人写的），把模型放进去，报告任务完成率。harness 是实验配置，不是被考的对象。但现实中 harness 带来的分数差比很多训练技巧还大，而且领域专用 harness 的需求越来越多——那「模型能不能自己当 harness 工程师」就成了真问题，却没人系统测过。

作者还有一层更深的论点：改 harness 和改普通代码不一样。改普通程序，要什么行为是外部说清楚的、对不对当场能验证；改自己的 harness，是在改「自己借以行动的基底」——改动会改变模型此后在所有任务上怎么观察、怎么规划、怎么恢复。做不好这一点，就只是把网上见过的 agent 范式抄一遍。

这套工作是一部曲里的第三部：Aspire 管「找对优化目标」，S³Gym 管「从经验里学对东西」，HarnessDev 管「让正确的改变在系统里持久」。前两部的发现可以一句话概括：系统可以「执行了一次更新」却并没有在优化预期能力，可以「积累了一堆经验」却没学出更好的策略。这一部专测系统层——项目页对这层的概括是「改外壳容易，把一个真正起作用的机制集成进去难」。

为什么系统层最难？因为前两层的改动是「一次性的」（改个目标、存条经验），系统层的改动却会反过来改变此后每一次执行——你改的是自己脚下的地板。这也是为什么这篇论文特意把「写外壳的模型」和「用外壳干活的模型」拆成两个角色来测：不拆开，你就分不清分数涨是模型聪明了还是外壳顺手了。

## 基准怎么设计

**Creation（从零造）：** 每个模型拿到统一的弱种子（能跑、零分）、任务族说明、权限约束、一份教程、1–3 个示例。看不到人类实现和隐藏考题。产出冻结后由执行模型在下游基准上跑。四个领域五个基准：SWE-bench Pro（731 题）、Terminal-Bench 2.1（89 题）、MLE-bench（75 题）、EQ-Bench3 写作（46 题）、BrowseComp 搜索（1,266 题），共 2,207 个任务。每组独立造 3 次取平均。两种口径：自己用自己造的（Self-Eval），和统一换成 Gemini 用（Unified-Eval）。

**Evolution（持续养）：** 从自己造的代码 harness 起步，控制器只负责跑评测、把分数写进事件日志，其余一概不管——不替你决定收不收某个版本、不回滚、不总结失败原因。改什么、何时提交、选哪个版本当最终交付，全是模型自己的事。每个候选版本冻结后要跑完整的「100 个 SWE 任务 + 89 个终端任务」两腿评测才算官方版本；跑了一半断掉的只能算诊断信息，不算成绩。9 条血统（5 条自己用自己 + 4 条固定 Gemini）共 73 个官方版本。全部结束后，每个版本都补测 630 个没见过的 SWE 任务，分数永不回传。

**防作弊：** 硬编码答案、偷看判分脚本、篡改日志、访问金标，一概禁止，逐版本逐任务审计，违规记零分。而且每次运行都保留轨迹和执行产物，事后能复查「交付的代码」和「这代码实际干了什么」是不是一回事。全文所有运行审计结果是零违规——没有一个 harness 作弊成功。

## 跑出来的效果

**造（Self-Eval，三副本平均）：**

| 模型 | SWE | 终端 | ML实验 | 写作 | 搜索 | 平均 |
| --- | --- | --- | --- | --- | --- | --- |
| 种子 | 0 | 0 | 0 | 0 | 0 | 0 |
| Opus 4.8 | 69.3 | 64.8 | 32.9 | 84.6 | 52.4 | **67.8** |
| Gemini 3.1 Pro | 43.6 | 68.8 | 32.4 | 74.8 | 35.2 | 55.6 |
| GPT-5.5 | 32.8 | 52.1 | 19.1 | 83.0 | 52.6 | 55.1 |
| DeepSeek V4 | 28.9 | 35.6 | 19.6 | 75.4 | 40.9 | 45.2 |
| Qwen 3.7 Max | 33.5 | 41.3 | 3.1 | 68.7 | 32.3 | 44.0 |
| Seed 2.0 Pro | 10.8 | 6.0 | 5.3 | 71.1 | 3.2 | 22.8 |
| 人类工程参照 | 80.0 | 88.8 | 24.0 | 83.7 | 92.2 | **86.2** |

几个读数：

- 写作基本追平（84.6 对 83.7），机器学习实验反超参照（32.9 对 24.0）；代码和搜索差距大（搜索最高 53.6 对 92.2）。
- 77.8% 的失败机器学习任务归因于 harness 缺陷，不是模型不行。
- 换成统一 Gemini 执行，排名洗牌：Qwen 44→52.8、Seed 22.8→29.8、DeepSeek 45.2→48.8 上升，Opus 67.8→53.3、GPT-5.5 55.1→44.8 下降——有些 harness 离了自己的「本命模型」就不行。
- 一个反直觉发现：加的代码越多成绩越好是错的。Gemini 总共只加了 1,006 行（全场最少），终端基准分却最高（68.8）；六个模型 18 份代码工件合计加 17,111 行，代码量不预测成绩。
- 模块体检暴露系统性缺口：18 份代码全部有执行循环，但状态管理只有 11 份定义了 State 类、只有 1 份能真正存状态；26,679 条任务轨迹里一次「保存状态」事件都没有。验证也大多是语法级的：2,325 个机器学习任务里 441 个交了空/坏的产出物，没有一个 harness 自己发现。

**养（Evolution，核心数字）：**

- 自己用自己的 5 条血统：可见分数全涨（+3.0 到 +13.9），未见任务也全涨但缩水到 +1.43～+4.44（均值 +3.11）。
- 逐次版本切换看：64 次可比切换里，可见分数和未见分数同方向的只有 34 次（53.1%）——跟抛硬币差不多。最能刷可见分的两条血统（Qwen +13.9、DeepSeek +13.4）恰好是未见分涨得最少的（+1.43、+3.17）。
- 9 个最终交付版里只有 2 个是各自血统里未见任务最优的。模型按「看得见的分数最高」挑版本，基本挑不中。
- 固定 Gemini 的 4 条血统：只有 Opus 在未见任务上涨（+2.70），Qwen 倒退 1.11、DeepSeek 倒退 2.38、GPT-5.5 崩掉 10.32。
- 过程解剖：中位交付版改 8 个文件（+476/−38 行）；64 次修改里 58 次动执行/控制流、37 次动工具，只有 4 次碰状态管理，没有一次碰独立验证器——模型养 harness 时只会在循环和工具上打转，够不到真正让能力持久的状态、记忆、验证模块。
- 崩掉的血统病根都能指认：有模型把步数上限硬编码成 120 步（换执行模型直接失效）；有模型做上下文压缩时把工具调用消息的配对关系弄坏；有模型加的「消息清洗器」误伤了合法的工具返回。

**一个正面案例值得单独讲。** Opus 演化时发现：100 个任务里 99 个 run 都报告「成功」，但判分显示只有 48 个真通过。它把这个差距追到「agent 过早宣布完成」，于是给 harness 加了一道完成检查。这是全文唯一被点名的成功样本，作者的总结是：反馈只有在「暴露一个具体失败模式、且后续改动被端到端验证」时才有用。

反面教材也现成：一个 GPT-5.5 候选版通过了全部 5 个抽样探针（小规模评测），全量评测只有 0.584——小探针和全量可以严重脱节，用探针成绩代替全量成绩会被坑。

还有一个「改了但没生效」的坑：论文检查了演化中新增的 169 个函数/类，只有 113 个真正从入口跑得到，56 个要么只被死代码引用、要么根本没人调用。改了代码不等于改了行为，得顺着执行路径确认。

## 别被结果骗了

- **「未见」其实没多未见。** 那 630 道题和 100 道反馈题出自同一个 SWE-Pro 公开拆分，判分程序一样、任务分布一样。这已经是最宽松意义上的 held-out 了，方向一致率还是只有一半；真换成别的任务族或别的判分方式，只会更惨。
- **样本太小，没做显著性检验。** 9 条血统、每个版本只跑一遍。+1.43 的提升和 −10.32 的崩溃，到底是真本事还是一次运气，论文没给统计检验。agent 基准单次跑分的抖动经常就有几分。
- **「追平人类」的两个项目有口径问题。** 写作和机器学习参照是作者本地复跑的成绩，而代码和搜索参照是外部最强公开报告——两套口径混在「平均 86.2」这一行里。「机器学习实验超过人类」这句话要打折读。
- **造得出来，可能主要是背出来的。** Creation 阶段每个模型只有 1–3 个示例，几乎没有学习信号——能造出 harness 靠的是预训练里见过多少现成范式（论文自己的行为分析就显示 Opus 一上来把种子重写成标准的工具调用循环）。真正测「从反馈里学」的是 Evolution，而那部分结论不乐观。
- **成本账只算了一半。** 表里的 token 只算执行模型干活的开销，模型在开发环境里写 harness 烧掉的 token 被明确排除。比较「谁造 harness 更划算」时这笔账是缺失的。

## 如果我要用这个思路

1. **给任何「自我改进」系统补一份隐藏复测。** 每个版本冻结后在开发者看不见的任务上补测，把「看得见的分数曲线」和「看不见的分数曲线」画到一张图上。两条线老分叉，就说明你的改进信号是噪声放大器。
2. **别让开发循环自己挑最终版本。** 保留全部版本轨迹，由外层用隐藏集（或多次重跑）做终选。本文 9 个自选终版只有 2 个选对。
3. **固定接口契约。** 统一的 CLI 入口、强制的 result.json（诚实标注成功/部分/失败）、轨迹文件、任务产物——让任何模型写的任何 harness 都能被同一个控制器冻结、评测、审计。这是整套流程能自动化的地基。
4. **换一个执行模型重测一遍。** 演化出的外壳换个底座模型还灵不灵，是必测项。重点盯两类改动：硬编码的步数/输出上限、和特定模型的消息格式耦合——本文里崩掉 10 分的血统，病根都是这两类。
5. **静态诊断三件套很便宜：** 净代码行数（不预测成绩）、六个模块的完成度（状态/记忆是普遍缺口）、新增代码可达性（本文 169 个新函数里 56 个不可达或无人调用）。不用跑评测就能发现「改了但没生效」的假改进。
6. **反馈要落在具体失败模式上并端到端验证。** 见上面 Opus 的完成检查案例。别用小探针替代全量评测。
7. **把回滚当一等公民。** 中位交付版删了 38 行；有模型大规模回滚重写后反而更好。自进化系统别只许前进——git 历史天然就是血统档案。
8. **把「正式成绩」的门槛抬高。** 只有完整跑完全量评测的版本才算数，跑一半的降级为诊断信息；抽样探针明码计价、预算耗尽自动关。这能防住「拿半截评测当成绩」。

## 名词小词典

| 术语 | 大白话解释 |
| --- | --- |
| harness | agent 的外壳：执行循环、工具、上下文、状态、恢复、验证。模型是发动机，这是驾驶舱 |
| 弱种子 | 只解析任务、写日志、啥也不干的兼容层，起点分恒为零 |
| Creation / Evolution | 两个阶段：从零造外壳 / 拿真实评测反馈持续改外壳 |
| creator / executor | 写外壳的模型 / 被塞进外壳里干活的模型，可以是同一个也可以拆开 |
| Self-Eval / Unified-Eval | 自己造自己用 / 所有外壳统一换 Gemini 用，后者才能公平比外壳本身 |
| 可见反馈 | 演化期能看到的 100 个 SWE 任务 + 89 个终端任务的分数 |
| held-out-630 | 630 个全程不给模型看的 SWE 任务，结束后才拿来考每个版本 |
| 声明版本 | 模型自己挑的最终交付版。9 个里只有 2 个是真最优 |
| 版本切换 | 相邻两个官方版本之间的一次改动。64 次里只有 34 次方向和 held-out 一致 |
| 血统 | 一个 creator 从自己的 H0 一路改出来的一条版本链，本文共 9 条 |
| 对分 | 演化期的报告口径：SWE100 和 Term89 两项分数的等权平均 |
| avg@3 | 每个模型独立造 3 份 harness 取平均，防止单次发挥不代表水平 |
| fixed-executor 消融 | 演化照旧、干活模型换成固定 Gemini 的对照实验，专测「进步是不是只伺候熟人」 |
| probe（探针） | 演化期的小规模抽样评测，计预算；和全量评测可能严重脱节 |
| 退化提交 | 程序跑完了但产出物是空/坏的，2,325 个机器学习任务里 441 个这样，没有一个 harness 自己发现 |

| seed-to-final diff | 从种子到最终版的代码差。案例里 Opus 一份 diff 净 +1252/−596，删除和回滚也是正常操作 |
| null result（审计） | 全部运行的合规审计结论：没有 harness 通过作弊路径得分 |
