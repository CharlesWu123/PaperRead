# 通俗版 · KnowAct-GUIClaw：让 GUI 助手记住上次是怎么点的

> 手机电脑上的操作助手，把成功路径存成可复用脚本，下次少摸索。

## 一分钟版本

- 场景：一个装在你手机/电脑上的助手，帮你点屏幕办事（订票、发消息、查订单）。痛点是每次都从零摸索。
- 做法：不训练模型。把跑过的轨迹提炼成两种东西存起来——一段文字教训（经验记忆），和一小段可执行的操作脚本（skill）。下次先查这两个库。
- 亮点：skill 不是无脑回放。每一步执行前都要先检查「现在屏幕是不是我预期的那一页」，不对就走恢复流程或退回普通点击。
- 数字：MobileWorld 的 117 个任务子集上，Kimi-K2.6 裸模型 55.6% 成功率，加上这套东西变 64.1%。小模型 Qwen3.5-35B 从 24.8% 升到 37.9%。
- 定位：这是工程集成做得很扎实的一篇，不是提出新演化机制的一篇。想抄工程细节值得读，想找演化算法可以跳。

## 它想解决什么问题

想象你让助手干一件事：「在手机上订一张明天去上海的高铁票，然后把车次发给老王」。

助手第一次要做的事：打开 12306，找到购票入口（可能藏在两层菜单里），填出发地、目的地、日期，选车次，确认。然后切到微信，找老王，把车次发过去。一趟下来可能点了二十多次屏幕。

明天你再让它订一张去杭州的票。理想情况它应该记得路径，直接冲到购票页。实际情况是：它又从首页开始摸索一遍。因为任务一结束，轨迹就被丢掉了。

原报告梳理了作者点出的四个具体缺陷：

1. **跨 app 传值会丢**。上一个 app 里查到的车次号，靠一段自由文本摘要传给下一个 app，容易丢或者被改写。反过来，如果强制要求用户说清「用哪个 app」，模型又会瞎猜 app。
2. **屏幕信息天生看不全**。截图、无障碍树、当前前台 app、历史动作，每一种都只是设备真实状态的一个侧面。谁都不完整。
3. **轨迹用完就扔**。成功的没留下路径，失败的没留下教训，下次照样踩。
4. **有快路径但不敢用**。Android 上有 deeplink 和 intent，一条命令直接跳到某个页面，比点二十次快得多。但没在真机上验证过就把它当长期 skill 用，很危险——manifest 里暴露了 `SEND` 常量不代表它真的能用、真的安全。

## 四个阶段怎么运转

系统分两层：一个大模型当 host（总指挥），一个小模型当 GUI executor（真正点屏幕的手）。默认配置是 Qwen3.5-397B-A17B 当 host + Qwen3.5-35B-A3B 当 executor。全程不改任何权重。

四个阶段是一个循环：

**Know（先摸清情况）**。动手前先查库：按语义相似度捞出相关的历史教训和候选 skill。关键点是这些东西**只是建议**，不覆盖你当前的指令。原文有个例子：任务是发 Mastodon 邀请链接，捞出来的教训说「手机端设置页不支持这个操作」，于是助手直接改道去 web 管理面板，而不是回放旧轨迹。host 还会在指令模糊时提出一个**明说出来、你可以否掉**的默认假设，而不是偷偷替你决定。

**Route（拆任务、签契约）**。host 决定这事是一个 GUI 任务还是一串跨 app 的工作流。每个子任务写成四件事：在哪个 app 域内做什么目标、可选地限定哪个 app、需要哪些输入、要返回哪些值。

这里有个设计值得单独说：跨子任务传值走一块**短命的黑板**，且是**声明式**的。子任务只能读黑板上声明过的输入，只能写声明过的输出。缺输入或者拿不到该返回的值，整个工作流**直接失败**（fail closed），绝不允许下游子任务自己猜一个值补上。回到订票的例子：如果「查车次」这一步没拿到车次号，那「发给老王」这一步不会启动，也不会编一个车次号发出去。

**Act（混合执行）**。可用动作分四类：普通 GUI 原语（点、滑、输入、返回、切 app 等）、skill、shortcut（Android deeplink/intent）、以及问用户。

skill 的运行时逻辑大致是这样：

```
每个子任务开始前：
  捞 Top-5 个 app 范围内的候选 skill（词法 + 向量两种信号）
  让模型判一下：用哪一个，或者全都不合适（可以全拒）

执行 skill 的每一步之前：
  有确定性契约就按契约校验当前屏幕
  没有就让视觉模型看一眼「这页对不对」
  不对的话三条出路：跑一个有边界的恢复子目标 / 跳过这个 optional 步骤 / 把控制权交回普通 GUI 执行
```

也就是说，skill 里稳定的字段（包名、坐标、intent 参数）事先写死，任务相关的值用占位符运行时填。deeplink 被包装成「一步 skill」，但只有目标页面、必需参数、app 状态都验过才用。

**Reflect（复盘写库）**。跑完之后决定要不要把这次经验存下来，以及怎么存。这是下一节的内容。

**把订票任务走一遍全流程**：

1. Know：host 收到「订明天去上海的高铁票，车次发给老王」。查库，捞到一条教训「12306 的购票入口在首页第二个 tab」和一条 skill「12306 查车次(出发地, 目的地, 日期)」。日期模糊，host 明说「我按明天算」。
2. Route：拆成两个子任务。子任务一：在 12306 域内买票，返回车次号。子任务二：在微信里把车次号发给老王，输入声明为车次号。
3. Act（子任务一）：候选 skill 过一道可用性判断，选中那条查车次的 skill。执行前先看屏幕——是 12306 首页，符合期望，继续。skill 跑到「选车次」这一步就交还控制权，因为选哪个车次不能写死在 skill 里，交回普通 GUI 执行。中途蹦出一个活动弹窗，被 optional 步骤挡掉。付款这一步不在 skill 里（危险动作黑名单），要么走 `A_ask` 问你，要么止步。车次号写回黑板。
4. Act（子任务二）：从黑板读车次号。如果这个值没拿到，这一步直接不启动，不会编一个发出去。
5. Reflect：这趟有新信号（有部分是普通 GUI 摸索出来的），于是把「12306 购票入口位置」写成一条文字教训，把新摸出来的稳定前缀提炼进 skill 库。如果整趟全靠已有 skill 跑完，什么都不写——没有新信号。

**跨平台是什么意思**：靠的是一张跨平台共用的动作表（Click、LongPress、Drag、Scroll、Type、Back、Home、Wait 这些共享，桌面多 Hotkey/OpenApp，移动端多 PressEnter）加统一的任务接口。**不是**某种平台无关的表示学习。skill 记录本身带 `platform` 字段，是绑平台的；shortcut 只覆盖 Android。所以「跨平台」指的是宿主接口统一，skill 资产并不跨平台迁移——原文没有明确讨论 skill 能不能跨平台复用。

## 记忆和 skill 是怎么攒起来的

这是全篇最值得看的部分。

**存两种东西**：

- **经验记忆**：纯文本，固定三段格式（标题 / 描述 / 内容）。成功和失败各有一套诱导 prompt，每条轨迹最多产 3 条，按 app 粒度去重。
- **skill 库**：可执行的参数化过程，用 Python DSL 写，长得像一串 `await action(...)`。每条带 app/platform 范围、参数、成功计数、有序步骤。每一步都有一个自然语言的期望状态（`valid_state`），可能还有一个结构化的屏幕契约（选择器集合 + sha256 指纹）。

**什么时候不写入**（准入门槛，这块设计得挺实用）：空轨迹、被取消、还没产生进展就超时、以及**完全由已复用 skill 完成的任务**。最后这条切断了 skill 库对自己成功案例的正反馈——不然库里会堆满同一模式的近重复条目。

**抽取不是录屏回放，是重写**。流程是：先把 GUI 事件重写成结构化证据（任务、平台、app、动作序列、参数、截图、控件线索、推断出的状态契约），然后让一个视觉模型在**约束极严的 prompt** 下只输出声明式动作序列。这套约束本身就是可以直接抄的工程资产：

- 函数体**只能**有 `await action(...)`。不许 if/for/while/try、不许赋值、不许计算、不许调 helper。
- 不许 f-string、字符串拼接、算术、比较、推导式。只能写字面量或占位符。
- 写死的值只能是可执行字段（x、y、text、key、包名、intent 参数），**绝不能**写死 `resource_id`、`content_desc`、`class` 这类选择器。
- 每个必需步骤必须有具体的期望状态。如果某个必需步骤想不出可验证的状态，那就删掉或重新生成这一步，而不是留空。
- 状态契约不许凭空发明选择器，只能照抄轨迹里给出的。
- 重复点击、乱点探路、无意义滚动都要丢掉。广告、权限、同意这类瞬时弹窗保留为 `optional=True`，不出现就跳过。
- **描述必须写泛化**：只能提 app 名、能力、粗粒度路径，参数角色用「query」「联系人」这种词。禁止嵌进具体标题、禁止写「official」「第一个结果」这类窄化限定词。
- **危险动作黑名单**：付款、删除、发送、提交订单、发布、不可逆的同意，一律不进 skill，除非原始任务明确要求。
- 失败轨迹也用：保留可复用的成功前缀。如果失败屏幕上明确写着一个安全的纠正动作，最多补一步，且不许为它编坐标。

**修复优先于新增**。这是个小而清晰的判断：只有当「没有失败的被复用 skill」时，系统才去挖新 skill。如果某条被复用的 skill 挂了，就把失败步骤、屏幕证据、报错、原始 skill 一起交给演化 prompt，**就地改这一条**，保留原 ID。允许的改动只有三种：把描述收窄、加一个带守卫的 optional 步骤、刷新过期的目标和状态契约。不许换成一个无关流程，不许加破坏性动作。

**有没有校验环节防止把错的记下来**：分开看。

- **skill 层面有**：每步状态契约或视觉校验，加上 shortcut 的真机验证闭环。shortcut 候选（从 manifest 挖出来的）只算「发现线索」，不算可信动作。必须在真机上实际拉起，记录前台 app、ADB 输出、UI 树、截图，再由 verifier 判定。只有 `page_validated` 的才能升级成一步 skill；只是「能拉起」的默认留在候选状态。
- **经验记忆层面没有**。文字教训只经过诱导 prompt 和去重，没有任何离线正确性验证。唯一的保护是「它只是建议，不覆盖指令」。原报告的判断是：这是整套设计里最松的一环。

另外，这套东西**没有淘汰机制**。失败的 skill 只被就地修复，不会被降权或删除；记忆条目只有「每任务上限 + 同 app 近重复丢弃」，没有全局容量上限，也没有老化。长期跑下来库会不会膨胀、检索会不会变噪，原文没讨论。

## 跑出来的效果

主战场是 MobileWorld 的 117 个 GUI-Only 任务子集，50 步上限，看一次成功率（pass@1），由 benchmark 自带的确定性打分器判定。

| 配置 | 成功率 |
| --- | --- |
| Qwen3.5-35B 裸 executor | 24.8% |
| 35B + host & 记忆 | 34.5% |
| 35B + host、记忆 & skill | 37.9% |
| 35B + host、Kimi 蒸馏来的记忆 & skill | 41.0% |
| 397B host 直接执行 | 46.2% |
| Kimi-K2.6 + host & 记忆 | 61.5% |
| Kimi-K2.6 + host、记忆 & skill | 64.1% |

怎么读这些数字：

- **提升是真的**。小模型 24.8% → 37.9%，Kimi 55.6%（裸模型）→ 64.1%。
- **SOTA 是真的，但边际很薄**。64.1% 只比 Seed-2.0-Pro 的 63.2% 高 0.9 点，比 GPT-5.5 的 62.4% 高 1.7 点。117 个任务里 1 个任务约值 0.85 点，所以这个优势相当于**多做对一个任务**。没有多次运行的方差报告。
- **skill 让精度升、成本降**，这是少见的组合。397B 上步数从 26.8 降到 23.7，token 降约 5%。原因是路径更短、截图观测更少。
- **但 skill 没有扩展能力边界**。只看真正调用了 skill 的任务：步数两档都是 −3.3，token −6% 左右，成功率 +4.9 和 +1.9，可是 pass@3 只有 +1.2 和 **+0.0**（63.2 → 63.2）。翻译一下：skill 让它「一次做对」的概率变高了，但那些它本来做不到的任务，给三次机会照样做不到。
- **记忆本身值多少分，这篇答不上来**。从 24.8% 到 34.5% 这 +9.7 点里，混着 host 编排、router、经验记忆三样东西，原文没有单独拆出记忆的贡献。而 host 编排本身就很值钱——让 host 自己接管合格的信息查询子任务后，GUI 调用次数从 2.5 降到 1.7，总 token 从 278k 降到 261k，host 自身 token 从 63.8k 降到 11.0k，同时成功率最高（46.2%）。
- **稳定性仍是短板**。最好配置下，三次里至少一次成功是 59.8%，三次全对只有 32.5%。也就是三分之一。
- **别的 benchmark**：AndroidDaily 上 resolved 78.61 分、all 64.89 分，baseline UI-TARS-1.5 是 56.64。注意 AndroidDaily 没有自带打分器，GUI 任务用 qwen3.5-flash 当裁判，要返回答案的任务由两位人类专家按 1.0/0.5/0 打分。作者自己承认 resolved 和 all 的差距里有相当一部分来自 app 可用性和环境不匹配，不全是策略质量问题。另外这个评测是在 iOS 设备上做的。
- **跨平台**：HarmonyOS 48/63（76.2%），Windows 21/30（70.0%）。这两个数用的是 qwen3.5-flash 判定或手工任务集，作者自己也只叫它 usability check，不能拿去和别人比。

正文有个小笔误：5.3 节写「+4.8」，但表格算出来是 40.6 − 35.7 = 4.9。以表格为准。

**没有演化曲线**。这点很关键：全文没有任何「成功率随运行轮次变化」的曲线，没有 skill 库规模随时间的统计，没有修复触发频次，没有 skill 命中率的时间变化。给出的是「有库 vs 没库」的二值对比。所以它更像一次性离线蒸馏出来的静态增强，而不是持续演化的证据。

另外，skill 和记忆是从 MobileWorld 轨迹蒸馏的，评测又在同一个 117 任务子集上。有没有跨任务或跨轮次的泄漏（比如同一任务先跑一遍产生 skill 再重跑），原文没交代。这直接影响那 +3.4 / +2.9 点该怎么读。

## 值不值得细读：坦率评价

原报告的结论一句话：**这是工程集成，不是新机制**。展开讲：

**记忆这一侧基本是搬运**。作者自己写了「灵感来自 ReasoningBank」，成功/失败双 prompt、每轨迹最多 3 条、去重，这套流程和 ReasoningBank 同构。新增的只是「按 app 解析结果」「同 app 内去重」这种领域适配。

**skill 这一侧是 Voyager 那套可执行 skill 库在 GUI 场景的重述**。真正有增量的是「每步状态契约 + 视觉状态校验」这一层：把回放脚本变成每步都验状态的守卫过程，加上 optional 步骤挡瞬时弹窗、危险动作黑名单。这些是扎实的、别处不容易照抄到的工程知识。但请注意它们属于**可靠性工程**，不是**学习机制**：没有效用估计，没有置信度更新，skill 之间没有组合和抽象层级，没有淘汰。

**只是特定场景适配的部分**，不构成通用机制：Android deeplink/intent 的挖掘与校验（强绑定 Android manifest 那套机制，换平台就没了）；`click_then_type` 这类复合动作（纯粹是 token 成本优化，和自演化无关）；跨平台动作表统一（工程必需品，没有理论内容）；MobileWorld 风格的 prompt 模板。

**最像「机制」的一块反而和自演化无关**：黑板的类型化契约 + fail closed。把跨 app 传值从自由文本摘要改成声明式输入输出契约，缺值就失败而不是编造。这是全篇最有原创感的设计判断，但它属于多 agent 工作流工程。

**和 DIVE、MetaSkill-Evolve 这类工作比，差距在哪**：那些工作明确提出了新的演化机制。这篇缺的正是机制层的东西——没有演化算子的形式化，没有增益随时间的分析，没有对「什么样的经验值得保留」给出可度量的判据（用的是 prompt 里的自然语言规则）。它的价值在于**把一堆已知机制在真实多平台设备上跑通了，并且把 prompt 契约和实验日志公开了**。

所以：

- **该读的人**：正在做 GUI agent、RPA、自动化脚本工程的人。你要的不是机制创新，是「怎么让 LLM 抽出来的脚本在真机上不崩」。这篇的 prompt 约束、状态守卫、真机校验闭环，都能直接抄进你的系统。做多 agent 跨步骤传值的人也可以只看黑板那一节。
- **可以跳的人**：想找自演化机制、看演化曲线、要形式化分析的人。这里没有。看 DIVE、MetaSkill-Evolve 这类更对路。
- **中间态**：如果你只想知道「记忆和 skill 到底值多少分」，这篇给不出干净答案——消融把 host、router、记忆捆在一起报了。

## 能拿走什么

1. **给每个 skill 步骤配双层状态守卫**。优先用确定性契约（结构化选择器 + 屏幕指纹哈希），退化时用自然语言状态描述让视觉模型判。不匹配时的三条出路提前定义好：有边界的恢复子目标、跳过 optional 步骤、退回通用执行。别让 skill 变成无守卫的回放脚本。
2. **抽取 prompt 用白名单 + 禁止清单，不要自由生成**。限定动作类型、禁止控制流和表达式、写死的值只许放可执行字段不许放选择器、必需步骤必须有可验证状态否则重新生成。代价只是 prompt 变长，换来的是可执行率和安全性。
3. **写入前设一个「无信号过滤器」，里面必须包含「完全由已复用 skill 完成」这一条**。这条比看上去重要：它切断了 skill 库对自身成功案例的正反馈，避免库里堆满同一模式的近重复条目。
4. **修复优先于新增，且修复必须就地**。失败时先判断是不是某个被复用的 skill 导致的。是的话只允许收窄描述、加带守卫的 optional 步骤、刷新过期目标，保留原 ID。只有不存在失败的复用 skill 时才去挖新的。
5. **危险动作黑名单要写进抽取和演化两处 prompt**。付款、删除、发送、提交订单、发布、不可逆同意一律不进 skill。这是把自演化放到真实设备上跑的前提条件，不是可选项。
6. **跨子任务传值用类型化契约 + fail closed**，别用自由文本摘要。每个子任务声明目标、app 范围、输入、输出，只读声明的输入，只写声明的输出，缺值直接失败。禁止下游子任务推断或补全缺失值——这是长链跨 app 任务里最容易被静默污染的地方。

另外提醒一个坑：这套 skill 里 `fixed_values` 会写死屏幕坐标（附录里拼多多搜索框写的是 x=242, y=88）。即使有状态契约校验，换机型分辨率或 app 改版后也只能靠演化 prompt 被动刷新。原文没有报告 skill 的失效率。

## 名词小词典

| 术语 | 大白话解释 |
| --- | --- |
| host / executor | 两层分工：host 是大模型总指挥，管拆任务和记忆；executor 是小模型，只负责真正点屏幕 |
| GUI task | host 派给 executor 的一个活。干完返回三样：完成没完成、干了啥的摘要、结束时屏幕长啥样 |
| 经验记忆 | 一段文字教训，三段格式（标题/描述/内容）。只当建议用，不能覆盖你的指令 |
| skill | 一小段可执行的操作脚本，带参数占位符和每步的期望状态 |
| shortcut | Android 的 deeplink / intent，一条命令跳到某页，绕开视觉点击。必须真机验过才用 |
| valid_state | 一句自然语言，描述执行这一步之前屏幕应该是什么样。给视觉模型判断用 |
| state_contract | 结构化版本的屏幕校验：一组选择器 + 一个 sha256 指纹。比自然语言更硬 |
| blackboard | 一块短命的共享区，跨子任务传值用。只能读写事先声明过的字段 |
| fail closed | 缺输入或拿不到该返回的值时，整个流程直接失败，绝不允许猜一个值往下走 |
| pass@1 / pass@3 | 一次做对的比例 / 给三次机会至少一次做对的比例。后者反映能力上限 |
| optional 步骤 | 标记为可跳过的步骤，专门用来对付广告、权限弹窗这类不一定出现的东西 |
