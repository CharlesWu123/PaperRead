# 通俗版 · MetaSkill-Evolve：不只改进做法，还改进「怎么改进」

> 别人让 AI 改进自己的操作手册，这篇让「改手册的规矩」也能被改。

## 一分钟版本

- 现在流行的做法：让 agent 把自己的操作手册（一份 SKILL.md 文本文件）越改越好。改手册的那套流程是人写死的。
- 这篇论文的说法：那不叫递归自改进，只是自改进。因为「怎么诊断失败、怎么提改法、给多少预算试」这些规矩从头到尾没变过。
- 它的做法：把改进流程也拆成五份同样格式的 Markdown 文件，让同一条流水线去改这五份文件。手册用快循环改，规矩用慢循环改。
- 模型权重完全冻结，只有一个 Gemma-4 31B 底座，五个 agent 共用它。所有提升都来自文本文件被改写。
- 效果：三个测试集上都比只改手册更好，多赚 +6.38 / +8.05 / +1.92 个百分点。但样本量只有 87~107 个，没有方差、没有多次随机种子、没有算力成本，证据比机制设计弱得多。

## 它想解决什么问题

打个比方。团队每周做复盘，照着一份复盘模板走：先找出最糟的那件事，再分析原因，再提改进措施。这套流程能让团队的《工作手册》越来越好。

但如果这份复盘模板本身有毛病呢？比如它规定「所有问题都按同一套五问法追根因」。那么不管是「看错了报表里的数字」还是「算错了一道账」，都会被塞进同一条分析路径。当这条路径给出错的结论时，复盘一百次也没人能修正复盘本身。

论文原文说得更狠：被优化的产物在变，优化它的算子不变。它点名批评了 EvoSkill、GEPA、SkillWeaver 这类系统，说它们是 self-improving，但达不到 recursively self-improving。

具体哪些东西被写死了？五件：失败怎么诊断、提出哪些改法、试错预算怎么分、别的分支的经验要不要拿来用、批准的改动怎么落盘。

作者还指出大家漏掉了一个量。评价一个演化分支，通常只看「当前手册考多少分」。但还有第二个量：这个分支照现在的改进规矩，能以多快的速度生出更强的后代。两者不等价——一份今天分数很高的手册，可能待在一个只会生出弱后代的分支上；一份中等分数的手册，可能待在一条能持续爬坡的路上，更值得投资。

论文也没吹过头。它明说自己是「有界的一层递归」：没有「改进改进流程的流程」这第三层。

## 核心思路：两层循环

类比：员工每天改进自己干活的方法，这是快循环。公司每季度开会改进「我们该怎么做复盘」这套制度，这是慢循环。制度变了，员工日常改进的方式就跟着变；员工这段时间改进得好不好，又是公司判断制度该不该动的依据。

快循环改什么：手册（task skill）。跑一批训练样本，挑出得分最低的那一个失败样本，诊断、提改法、写进文件，然后在验证集上打分。分数比父代高才算过关。

慢循环改什么：五份「规矩文件」，论文里叫 meta-skill。原文写成一个五元组的数学符号，翻成人话就是五个可调的部件：

- 管分析的：怎么给失败贴标签、怎么写诊断、指向该改哪个文件。标签词表本身也归它管，也能被改。
- 管检索的：从历史库里捞多少条同分支/跨分支的经验当灵感，宽一点还是深一点。
- 管分配的：这一轮生几个子代去试，1 到 3 个。
- 管提议的：具体改哪一节、改成什么、为什么。
- 管落盘的：把改动真正写进文件，并检查是不是写了个空改动。

每份规矩文件对应恰好一个 agent 读。慢循环不是每轮都跑，默认每 2 个快迭代跑一次。

虚构示例，看规矩被改前后的差别。改之前，管分析的部件里写着：

```
诊断步骤：读失败轨迹，用一句话说明为什么错。
标签词表：计算错误 / 检索错误 / 格式错误
```

慢循环发现最近几个子代平均只涨了 0.4 分，太慢了，于是把它改成：

```
诊断步骤：先判断错在「读数据」还是「用数据」，再定位到具体那一步。
标签词表：表格行列错位 / 单位换算错 / 多步算术中间量丢失 / 引用了过期检索结果 / 格式错误
```

标签变细之后，管检索的部件能捞到更贴题的历史经验，管提议的部件也能提更精准的改法。这就是为什么论文强调五份文件要一起改：如果提议部件已经假设了新的细标签，而分析部件还在用老的三个粗标签，就对不上了。

## 「同一条流水线作用于自身」到底怎么实现

这是最容易听成玄学的地方，实际做法很朴素，就两个技巧。

技巧一，表示统一。规矩文件和手册用的是同一种格式，都是 SKILL.md。所以那条「分析 → 检索 → 分配 → 提议 → 落盘」的五 agent 流水线不用改一行 prompt、不用加一个新组件，就能直接作用在规矩文件上。区别只是：加载的 skill 目录换成 meta 那一套，要改的目标文件换成 `skills/meta-analyzer/SKILL.md` 这类路径。

技巧二，把改进历史伪装成一个失败样本。快循环的 Analyzer 吃的是「一个失败的任务样本」。慢循环里没有这种东西——它要诊断的是「最近这几轮改得不够好」。作者的做法是：把最近 H 个子代的平均增益、这些轮的标签、诊断、结果打包序列化成一条合成的「失败轨迹」，喂给同一个 Analyzer。原文的说法是：把改进历史重塑成看起来像一个失败训练样本的东西，这样一个 Analyzer prompt 就能服务两个时间尺度。

慢循环和「多跑一遍快循环」有三点不同，这几点是它没退化成冗余的关键：

1. 兜底约束。如果诊断为空、或者诊断错误地指向了手册而不是规矩文件，就在五个部件之间轮流（round-robin）挑一个来改。这样慢循环不会中止，也不会静默变成一次没用的快循环。
2. 整体重写。每个子代一步里把五份文件全改一遍，提议按顺序生成，落盘五个文件并行写。保证跨部件一致。
3. 累积式子代。第 k+1 个子代读的是第 k 个子代写完的文件，不是父代的文件。所以那几轮是层层打磨，而不是各写各的最后互相覆盖。

另外，每个分支带自己的规矩文件，不共享全局状态。一条分支学到的改进策略要传到另一条分支，唯一通道就是 meta 层的检索。论文举的图景：一条分支面对表格抽取失败学会了激进的大改，另一条面对算术推理发展出保守的小步改。

工程上还有一点值得记：分支状态由数据库定义，不由工作目录里剩下的文件定义。每次展开一个父代之前，先把它的手册快照和规矩快照恢复到磁盘，跑完再存回去。所有搜索历史存成一张 SQLite 里的有向无环图，节点只创建不修改。

## 跑出来的效果

三个测试集，留出集准确率（%），底座是同一个冻结的 Gemma-4 31B：

| 方法 | OfficeQA | SealQA | ALFWorld |
| --- | --- | --- | --- |
| 什么都不加 | 31.78 | 29.17 | 92.31 |
| 加一份手写手册，全程不改 | 36.09 | 29.41 | 90.38 |
| 只开快循环（改手册） | 48.94 | 37.21 | 92.31 |
| 完整系统（再开慢循环） | 55.32 | 45.26 | 94.23 |

拆成三段看：

- 只是加一份手写手册：OfficeQA +4.31，SealQA +0.24（基本没用），ALFWorld −1.93（还退步了）。光有工件不解决问题。
- 把固定手册换成会自我改进的手册：再加 +12.85 / +7.80。ALFWorld 只是回到不加手册的水平。
- 打开慢循环：再加 +6.38 / +8.05 / +1.92。这就是「递归到底值不值」的那一格。

换成占比更直观：SealQA 上慢循环贡献了端到端提升的 50.0%，跟快循环几乎一样多；OfficeQA 上是 27.1%；ALFWorld 上是 100%——因为前两步在那个任务上净收益是零，全部提升都来自慢循环。作者据此说：即使手册演化已经饱和，改进规矩仍然是起作用的那个成分。

拆掉单个部件看谁重要（完整系统 55.32 / 45.26 / 94.23）：

- OfficeQA 上「管分配的」最要命，掉到 35.58，也就是 −19.7 点。解释是这个任务里有成片相关的算术错误，卡住的时候必须自动加宽试错预算才可能碰出一个好子代。
- SealQA 和 ALFWorld 上「管提议的」最要命，分别掉到 36.84 和 86.54。这两个任务吃的是每次改动的精确内容，不是搜索扇面。
- ALFWorld 上单独关掉跨分支检索，成绩正好回到只开快循环的 92.31。所以那 +1.92 全部来自跨分支复用子程序。

慢循环触发频率：固定做三次规矩更新，迭代数随间隔缩放。

| 测试集 | 每 2 轮更新一次 | 每 4 轮 | 每 8 轮 |
| --- | --- | --- | --- |
| OfficeQA | 48.94 | 41.35 | 39.84 |
| SealQA | 44.14 | 44.14 | 43.24 |
| ALFWorld | 90.38 | 90.38 | 88.46 |

最勤地更新最好，但幅度看任务。OfficeQA 从 2 到 8 掉 9.1 点，另两个几乎持平。作者的解释是双向的：更新太勤，规矩文件就暴露在本来想过滤掉的单样本噪声下；更新太懒，规矩相对手册就过时了，它那种大范围重写会盖掉快循环已经攒下的好改动。

还有一条实用发现：在底座本来就做得很好的任务上，验证集太小会让慢循环完全空转——失败样本太少，分析部件根本看不到失败轨迹，整条链没信号。ALFWorld 上把验证集比例从 0.10 提到 0.25，分别涨 +2.0 / +4.3 / +2.5 点。

## 别被结果骗了：几个要留意的地方

- 样本量太小，还没给方差。作者自己在附录里披露每个测试集大约 87 到 107 个样本，但主结果没写样本数、没写跑了几个随机种子、没有标准差和置信区间。SealQA 那 +8.05 点大约等于 7 到 9 个样本。ALFWorld 那 +1.92 点相当于约 2 个 episode，基本在噪声量级，作者却拿它当「即使手册饱和 meta 仍有效」的证据，这个论断很单薄。
- 算力成本一个字没提。慢循环每轮要顺序生成 5 份提案、并行写 5 个文件，还要乘子代数；快循环每个子代都要在验证集上完整跑一遍。相对只开快循环，token 和调用量翻了几倍，原文没给。所以「+6.38 点」值不值那份额外算力，无法判断。而且间隔 sweep 固定的是更新次数而不是总算力，正好绕过了这个对比。
- 对照组被砍了三样东西，不只一样。只开快循环那组同时被限制成「每轮只生 1 个子代」「不许跨分支检索」「不更新规矩」。所以那 +6.38 / +8.05 里混着「预算能大于 1」和「能跨分支借经验」这两个跟递归无关的因素。作者却写「与对照组唯一的差别就是规矩文件是否被演化」，这跟他们自己对对照组的定义不一致。消融表说明实现上两个配置是同一个，所以矛盾出在描述，但归因确实说过头了。
- 只有一个底座、一个规模。全部实验都是 Gemma-4 31B。让模型读懂「关于自己诊断流程的自然语言指令」并改写它，这个能力很可能强依赖模型规模。换模型换尺寸能不能复现，完全没测。
- 「改进速度」这个量本身估得很糙。每轮最多 3 个子代、总共 5 轮，意味着大多数节点的这个估计只是 1 到 3 个子代增益的平均，没有子代的节点直接记 0。而它在选父代的打分里占了权重 0.5。作者承认另一项置零时会「把噪声很大的单子代增益当父代质量」，却没量化这一项自身的噪声。
- 没有证据说明递归收益会累积。递归自改进的核心主张应该是「改进流程变好之后，后续改进速度加快」。原文没有给出任何「改进速度随迭代上升」的曲线，而且在间隔 sweep 里迭代从 6 增到 24 时成绩反而下降。所以这篇证明的是「演化改进规矩有用」，不是「递归带来复合增长」。
- 一个反常但重要的细节：打开慢循环却废掉某一个部件，成绩掉到 35.58~40.54，比彻底不开慢循环的 48.94 更差，OfficeQA 上甚至低于静态手册的 36.09。原文没讨论。含义是：慢循环是个会主动重写自己诊断和提案逻辑的机制，部件不完整时它会把系统推到比不动更糟的地方。它的防退化手段只有「分数没涨就不许当父代」这一条纯选择式规则，落盘时的哈希校验只能抓「文件其实没改」的空改动，抓不了「改了但改坏了」。

## 如果我要用这个思路

1. 先加最便宜的那个技巧：写一个函数，把最近几轮的平均增益、标签、诊断、结果序列化成一条「假的失败样本」，喂给你现有的诊断 prompt。任何已有的「分析→提议→改写」系统都能加，不需要为 meta 层单写 prompt。
2. 让 meta 层和 task 层用同一种表示（都是 Markdown 手册）。一旦 meta 层用代码或专用配置，你就得为它再写一套算子，递归的成本立刻上去了。
3. 分支状态存数据库，别靠工作目录。每次展开父代前把快照恢复到磁盘，跑完存回去。这样不同分支之间不会互相污染文件，任何结果都能追溯来源。
4. 失败和没提升的子代不要删，降级成「只能当灵感被检索」。一个失败的改动对后面的提案仍有信息量，实现成本几乎为零。
5. 选下一个父代时别只看分数。加上「这个分支最近的产出速度」和「这个分支被选过几次」两项，防止算力被一条线垄断。论文默认权重是 1.0 / 0.5 / 0.25。
6. 在基线本来就很高的任务上，先把验证集做大，否则失败样本太少，整套自改进机制会空转。
7. 五个部件要一起改、层层累积地改，别各改各的最后平均掉。同时给诊断环节加解析失败的兜底路径，否则慢循环会悄悄退化成一次没用的快循环。

## 名词小词典

| 术语 | 大白话解释 |
| --- | --- |
| task skill | agent 干活用的操作手册，一份 Markdown 文件，写明流程、工具和经验规则 |
| meta-skill | 「怎么改手册」的规矩，同样是 Markdown 文件，一共五份，分别管分析、检索、分配、提议、落盘 |
| 快循环 | 改手册的那层循环，每轮挑一个最糟的失败样本来改 |
| 慢循环 | 改规矩的那层循环，默认每 2 个快迭代触发一次，看的是这段时间的平均战绩 |
| 任务效用 | 手册在验证集上的得分，也就是「现在干得多好」 |
| meta 生产力 | 这个分支照现在的规矩，平均每个子代能涨多少分，也就是「进步得多快」 |
| 演化图 / archive | 存在 SQLite 里的搜索历史，节点只新增不修改；只有分数比父代高的子代才进 archive、才有资格当下一轮父代 |
| frontier | 每轮从 archive 里选出的候选父代池，按「分数 + 产出速度 + 冷却」三项打分挑一个展开 |
| 跨分支检索 | 从别的演化分支捞经验当灵感，也是不同分支之间传递改进策略的唯一通道 |
| 有界的一层递归 | 规矩能被改，但改规矩用的那五个角色和它们的接线是写死的，没有第三层 |
